# Лабораторная работа №1

## Тема

Первое знакомство с большими языковыми моделями через API

## Цель

Освоить базовый программный цикл взаимодействия с LLM и научиться сравнивать несколько моделей на одинаковом наборе заданий.

## Задачи

1. Подключиться к API минимум двух LLM (Python-клиент).
2. Подготовить единый набор из 10+ запросов разных типов (объяснение, классификация, суммаризация, извлечение данных, код, отладка, аналитика, ИБ, деловой текст, формат).
3. Прогнать набор через каждую модель, измерить задержку, сохранить ответы и ошибки в CSV/JSON.
4. Оценить каждый ответ по критериям: корректность, полнота, следование инструкции, практическая полезность (0–2 балла).
5. Сделать сравнительный вывод о применимости каждой модели.

## Используемые технологии

- Python 3.10+
- Ollama (локальный сервер, OpenAI-совместимый API `http://localhost:11434/v1`)
- Библиотека `openai`, `python-dotenv`

Модели (локальные, через Ollama, дата эксперимента 2026-09-30):

| Модель | Размер | Расположение |
|---|---|---|
| `llama3.2:1b` | 1.3 GB | локально (CPU) |
| `qwen2.5:1.5b` | 986 MB | локально (CPU) |

## Запуск

```bash

ollama serve            # если сервер ещё не запущен
ollama pull <model>      # скачать нужные модели
python src/main.py
```

## Описание решения

Клиент (`src/main.py`) обращается к обеим моделям через один и тот же OpenAI-совместимый интерфейс `client.chat.completions.create`, меняется только параметр `model`. Такой подход выбран потому, что Ollama предоставляет OpenAI-совместимый REST API (`/v1`), поэтому переключение модели не требует изменения кода — только имени модели в `.env` (`LLM_MODELS`, список через запятую).

Модели выбраны локальные (через Ollama), а не облачные, потому что:
- не нужен API-ключ платного провайдера;
- эксперимент полностью воспроизводим офлайн;
- обе модели достаточно компактны (1–1.3 ГБ), чтобы работать на CPU без GPU в разумное время.

Для каждого запроса измеряется задержка через `time.perf_counter()` до и после вызова API. Ошибки вызова не прерывают эксперимент — они перехватываются `try/except`, фиксируются в результате отдельным полем `error` и не приводят к потере остальных данных (раздел 8.4 методических указаний). Сырые ответы сохраняются в `results/raw_results.json` (полный текст) и `results/results.csv` (сокращённый превью на 200 символов, для быстрого просмотра). Ручная оценка по 4 критериям (корректность / полнота / следование инструкции / практическая полезность, 0–2 балла) вынесена в отдельный файл `results/scores.csv`, так как автоматически её посчитать нельзя — нужна проверка человеком.

Тестовый набор (`src/prompts.py`) содержит все 10 типов заданий, рекомендованных методичкой (раздел 8.3): объяснение, классификация, суммаризация, извлечение структуры, код, отладка, аналитика, ИБ-задача, деловой текст, жёсткий формат ответа.

### Сводное сравнение моделей

| Модель | Средний балл /8 | Средняя задержка, с | Ошибки API | Лучшие задачи | Слабые задачи | Краткий вывод |
|---|---|---|---|---|---|---|

| qwen2.5:1.5b | 5.2 | 70.9 | 0 | Объяснение, ИБ, классификация | Код | Заметно более связная и фактически точная модель, но втрое медленнее |

Характерный пример разницы в качестве — задача №1 («Объясни разницу между хешированием и симметричным шифрованием»): `llama3.2:1b` дала фактически неверный и местами нечитаемый ответ (смешение русских и иностранных слов), `qwen2.5:1.5b` — связный и корректный ответ по существу (полный текст — в `results/raw_results.json`).

## Вывод

В ходе эксперимента подтвердилось, что даже в пределах одного семейства «малых» локальных моделей (1–1.5 млрд параметров) качество ответов может различаться в разы: `qwen2.5:1.5b` набрала в среднем 5.2 балла из 8 против 1.6 у `llama3.2:1b`, стабильно превосходя её на содержательных задачах (объяснение, классификация, ИБ-задача, форматированный вывод). Расплата за качество — задержка: `qwen2.5:1.5b` в среднем вдвое медленнее (70.9 с против 35.2 с на CPU без GPU).

Ни одна из моделей не справилась хорошо с задачей написания кода (0 и 2 балла соответственно) — обе сгенерировали функции, не решающие поставленную задачу корректно, хотя и синтаксически похожие на решение. Это показывает, что для задач генерации кода модели такого размера (1–1.5B) непригодны без дополнительной проверки/тестирования сгенерированного кода — печатный листинг нельзя использовать «как есть».

Для интерактивного ассистента с требованиями к качеству текста (объяснения, ИБ-анализ, деловая переписка) стоит выбрать `qwen2.5:1.5b`, несмотря на более высокую задержку. Для задач, где важна скорость, а результат используется только как черновик под ручную правку (например, быстрая черновая классификация с последующей проверкой человеком), можно рассмотреть `llama3.2:1b`, но с обязательной проверкой из-за риска несвязных ответов. Для продакшен-сценариев обе локальные модели такого размера уступают более крупным облачным моделям по фактической точности — это ожидаемо, так как задача лабораторной была сравнить модели между собой, а не найти готовое к внедрению решение.
