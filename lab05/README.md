# Лабораторная работа №5

## Тема

Развёртывание и исследование локальной большой языковой модели

## Цель

Получить практические навыки развёртывания LLM на локальном компьютере, подключения к ней программного клиента через API, измерения требований к вычислительным ресурсам и производительности, сформировать понимание преимуществ, ограничений и рисков локального применения LLM.

## Описание решения

Клиент (`src/client.py`) обращается к Ollama напрямую через `/api/generate` (а не через OpenAI-совместимый `/v1`, как в остальных лабах) — ровно так, как показано в базовом примере методички, чтобы продемонстрировать работу с «родным» API среды выполнения, а не только с OpenAI-подобной прослойкой.

**Инцидент и исправление.** Первый прогон завис: Ollama вернула `500` после `3m0s` на одном из запросов (видно по `results/` и логам сервера), после чего процесс завис на `futex_wait` без сетевой активности ещё ~20 минут — на момент зависания `free -h` показывал 8.7 ГБ в swap из 14 ГБ RAM, то есть машина была в состоянии реальной нехватки памяти. Причина — задание 5 изначально принудительно выгружало модель (`keep_alive=0s`) перед измерением «baseline до загрузки», и повторная загрузка под памятным давлением спровоцировала зависание сервера. Решение: убрал принудительную выгрузку (риск важнее академической чистоты «чистого baseline»), снизил клиентский таймаут с несуществующего (180с) до 90с, обернул каждый вызов в `try/except` вместо падения всего скрипта, добавил промежуточное сохранение после каждого этапа. После перезапуска 8 вызовов всё равно словили таймаут 90с (сервер отвечал за 60–95с — это нормальная скорость для 1.5B модели на этом CPU, а не зависание), поэтому они точечно передопрошены отдельным скриптом `retry_failed.py` с таймаутом 150с — все 8 завершились успешно без повторных проблем. Это реальный, а не теоретический урок про эксплуатационные риски локальных LLM, упомянутый в разделе 5 методички («требования ИБ») — сам факт нехватки ресурсов является эксплуатационным риском.

**Наблюдение, расходящееся с ожиданием методички:** первый запуск оказался *быстрее* среднего повторного (75.4с против 94.2с), хотя обычно первый запуск медленнее из-за загрузки модели в память. Разброс по времени ответа (73–124с) почти полностью объясняется разной длиной сгенерированного ответа (308–516 токенов) при стабильной скорости генерации, а не нестабильностью самой системы.

## Индивидуальное задание

Сценарий: локальный прототип классификации событий ИБ (`src/individual.py`) — принимает текст события, вызывает `qwen2.5:1.5b` через `/api/chat` с системной инструкцией, возвращает JSON `{risk_level, reason, recommended_action}`. Запускается как `python individual.py "<текст события>"` для одиночного запроса или без аргументов — демонстрация на 5 примерах.

_Результат демонстрации — после отдельного прогона (см. `results/individual_demo.json`)._

Локальное размещение для этого сценария оправдано: входные данные (события ИБ) потенциально чувствительны и не должны покидать периметр, а задержка в десятки секунд приемлема для асинхронного SOC-пайплайна (не интерактивного чата).

## Вывод

Локальная LLM масштаба 1–1.5B параметров на CPU без GPU — рабочий, но медленный инструмент: типичная задержка ответа 30–130 с, что совершенно неприемлемо для интерактивного чата, но приемлемо для фонового/пакетного анализа (классификация логов, пред-обработка инцидентов). Скорость генерации (ток/с) оказалась куда стабильнее общей задержки — колебания времени ответа почти полностью объясняются длиной сгенерированного текста, а не нестабильностью системы, что важно для оценки SLA. При этом сама инфраструктура — не только модель — требует внимания: на машине с 14 ГБ RAM и уже используемыми ~10.5 ГБ до эксперимента операция выгрузки/перезагрузки модели реально спровоцировала зависание сервера; для продакшен-развёртывания это означает, что запас RAM и консервативные операции управления жизненным циклом модели не менее важны, чем выбор самой модели. Сравнение двух моделей показало классический компромисс: `llama3.2:1b` втрое быстрее, но заметно чаще ошибается по существу (включая генерацию синтаксически некорректного кода), тогда как `qwen2.5:1.5b` медленнее, но содержательнее — однако не свободна от собственной нестабильности (отказ на том же JSON-запросе, который сама же успешно выполнила парой заданий раньше). Для сценариев, где задержка в пределах минуты приемлема, а данные не должны покидать периметр (разбор событий ИБ, внутренние логи), локальная модель такого масштаба пригодна при условии последующей проверки результата; для интерактивных пользовательских сценариев с требованием ответа за секунды она не подходит — здесь выбор смещается либо к более мощному железу (GPU), либо к облачной модели (что исследуется в ЛР6).
