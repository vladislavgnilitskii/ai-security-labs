# Лабораторная работа №6

## Тема

Сравнение локальных и облачных больших языковых моделей: качество, производительность, стоимость и безопасность

## Цель

Научиться обоснованно выбирать архитектуру применения LLM, сопоставляя качество ответа, задержку, пропускную способность, стоимость, требования к вычислительным ресурсам, приватность данных и эксплуатационные риски.

## Выбранный сценарий

Прикладной сценарий — обработка типовых задач SOC/службы поддержки: классификация событий ИБ, извлечение структурированных данных из заявок, краткий анализ риска, работа с кодом/логикой (продолжение сценариев ЛР1–ЛР4).

## Модели

| Роль | Модель | Провайдер |
|---|---|---|
| Локальная | `qwen2.5:1.5b` (Q4_K_M) | Ollama, `http://localhost:11434/v1` |
| Облачная | `liquid/lfm-2.5-2.6b:free` | OpenRouter, `https://openrouter.ai/api/v1` |

### Сетевое ограничение

Используемый облачный провайдер (OpenRouter) блокирует запросы с IP-адресов, определяемых как российские (`403 Access denied by security policy`), независимо от валидности API-ключа. Для выполнения работы облачный клиент маршрутизируется через личный SOCKS5-прокси с зарубежным узлом (переменная `CLOUD_HTTP_PROXY` в `.env`, не коммитится в репозиторий). Это сознательно задокументированное окружение-специфичное решение: сам факт недоступности облачного API по сети без обхода блокировки — тоже значимое наблюдение для раздела анализа ИБ/эксплуатации (зависимость от поставщика и геополитических ограничений доступа).

Бесплатная модель OpenRouter использована потому, что она даёт реальный облачный API без расходов; в рамках задания по стоимости (раздел «Расчёт облачной стоимости») это явно учтено — `cost: 0` для данного тарифа, вместе с объяснением, как считать стоимость для платной модели.

## Описание решения

Единый клиент (`src/providers.py`) создаёт два `openai.OpenAI`-инстанса с одинаковым интерфейсом вызова (`src/metrics.py:timed_call`) — различается только `base_url`/`api_key`/сетевой транспорт. Для облачного клиента, если задан `CLOUD_HTTP_PROXY`, используется кастомный `httpx.Client` с SOCKS5-прокси; локальный клиент всегда подключается напрямую. Это сделано, чтобы код эксперимента не содержал условной логики "если прокси — то..." в местах, где выполняются замеры — вся сетевая специфика инкапсулирована в `providers.py`.

Тестовый набор — **20 заданий, 4 типа по 5** (`data/test_cases.json`): классификация событий ИБ, извлечение данных в JSON, краткий анализ риска, работа с кодом/логикой — ровно по структуре раздела 5.1 методички. Для 5 заданий (по одному каждого типа + дубль «код») выполнено по 3 дополнительных прогона на обеих моделях для оценки устойчивости (`results/repeat_results.csv`).

**Инцидент при первом прогоне и его причина.** Первая попытка (до появления работающего прокси) не могла даже стартовать: облачный провайдер (OpenRouter) возвращал `403 Access denied by security policy` на любой запрос с IP текущей сети — подтверждено прямым `curl` независимо от валидности ключа. Это не ошибка кода, а реальное сетевое/геополитическое ограничение доступа к облачному API, и само по себе является значимым наблюдением для раздела анализа ИБ ниже (см. «Зависимость от поставщика»). Решение — личный SOCKS5-прокси с зарубежным узлом, подробности в README-разделе «Сетевое ограничение» выше.

### Пример расхождения в качестве (T19, `==` vs `is` для токенов безопасности)

Локальная модель дала **самопротиворечивый** ответ: привела дважды один и тот же код (`token = "admin"; new_token = "admin"`) с противоположными комментариями о результате — сначала `token == new_token  # True`, `token is new_token  # False`, затем тот же код с комментариями `# False, значения не равны` / `# True, значения и адреса равны`. Облачная модель дала связное и корректное объяснение с реалистичным примером валидации JWT и правильной рекомендацией использовать `==`, а не `is`, для сравнения токенов. Это главный источник разрыва в оценке качества — не единичный случай, а системное наблюдение: аналогично в T07 локальная модель проигнорировала явное требование «Извлеки поля в JSON» и выдала обычный текстовый список вместо JSON.

Полные тексты всех ответов — `results/raw_results.csv`.

## Расчёт облачной стоимости

Использованный тариф (`liquid/lfm-2.5-2.6b:free`, проверено через `/api/v1/models` 24.10.2026): `prompt: $0`, `completion: $0` — полностью бесплатный тариф OpenRouter.

Фактический расход токенов на 20 заданий: **1477 входных + 13883 выходных** (в среднем 694 выходных токена на ответ — модель генерирует развёрнутый внутренний reasoning-трейс, который также тарифицируется как completion-токены у платных моделей). Стоимость тестового набора: **$0**.

Формула расчёта для гипотетической платной модели с ценой `Pвх`/`Pвых` за токен (раздел 2.4 методички):

```
C = Nвх · Pвх + Nвых · Pвых
```

Для иллюстрации (не реальная цена конкретного провайдера, а порядок величины для сопоставимой компактной модели на рынке на конец 2026): при `Pвх ≈ $0.1/1M` и `Pвых ≈ $0.3/1M` токенов, naш набор обошёлся бы примерно в `1477×0.0000001 + 13883×0.0000003 ≈ $0.0042` — то есть даже платная модель такого класса стоила бы копейки на 20 запросов; при расчётной нагрузке 100 000 аналогичных запросов — ориентировочно **≈$21**. Нулевая цена API для бесплатного тарифа не означает нулевую стоимость эксплуатации системы: сохраняется стоимость разработки, мониторинга, интеграции и — в нашем случае — дополнительной инфраструктуры обхода сетевых ограничений (личный прокси-сервер).

**Контрольная точка ИБ.** Для выбранного сценария (SOC/обработка заявок) допустимо отправлять в облако: обезличенные/синтетические описания событий, не содержащие реальных IP, имён сотрудников, доменов организации. Требуют обезличивания: реальные тикеты техподдержки с ФИО и контактами. Должны обрабатываться только локально: журналы с реальными данными клиентов (как в тесте T09 — запрос на удаление ПДн), внутренние несогласованные инциденты до их формальной классификации.

## Дополнительное задание: гибридная архитектура

Правило маршрутизации (по методичке, раздел 9): данные с персональной/конфиденциальной информацией или относящиеся к нераскрытому инциденту — всегда локально; обезличенные задачи с высокими требованиями к скорости и формату — в облако.

```python
def choose_backend(task):
    if task.contains_personal_data:
        return "local"
    if task.confidentiality == "high":
        return "local"
    if task.type in ("extraction", "classification") and task.complexity == "low":
        return "cloud"   # облако заметно быстрее и строже держит формат JSON
    return "local"
```

Решение о маршруте **не должно приниматься самой LLM** — в показанном коде маршрутизация основана на явных программных признаках задачи (наличие ПДн, уровень конфиденциальности), заданных вызывающей системой, а не определяемых моделью по тексту запроса. Это прямо следует из наблюдения в ЛР3: модель нельзя считать надёжным механизмом соблюдения политик безопасности — её собственное решение «это не содержит личных данных» столь же ненадёжно, как и остальные её ответы.

## Вывод

Прямое сравнение на 20 заданиях показало, что облачная модель (даже на бесплатном тарифе) превосходит локальную `qwen2.5:1.5b` на этом CPU-only стенде одновременно по трём независимым осям: скорости (в 3.7–10.6 раза быстрее в зависимости от типа задания, разрыв растёт с длиной ответа), качеству (средняя оценка 2.0/2 против 1.38/2 на представительной выборке из 8 заданий, 100% против 50% полностью корректных ответов) и предсказуемости (меньший разброс задержки на всех 5 повторных тестах). Главные провалы локальной модели — не случайные опечатки, а системные: нарушение явного формата JSON (T07) и самопротиворечивый, фактически неверный ответ на вопрос о сравнении токенов безопасности (T19) — именно в задаче, где цена ошибки для реальной системы была бы высокой. При этом локальная архитектура сохраняет безальтернативное преимущество там, где качество и скорость вторичны по сравнению с конфиденциальностью и независимостью от сети: сама эта лабораторная наглядно показала зависимость облачного варианта от внешних факторов, недоступных локальной модели — запрос был заблокирован по геопризнаку, протестированный ключ столкнулся с временным сбоем провайдера, а доступ потребовал нетривиальной сетевой инфраструктуры обхода ограничения. Рекомендация по стоимости и по безопасности не всегда совпадает с рекомендацией по качеству: для сценария «внутренние документы ИБ» правильный выбор — локальная модель несмотря на её более низкое качество, просто потому что цена утечки данных перевешивает цену медленного и местами ошибочного ответа. Гибридная архитектура с программной (не LLM-based) маршрутизацией по уровню конфиденциальности задачи — разумный компромисс, который этот эксперимент подтверждает количественно, а не декларативно.
